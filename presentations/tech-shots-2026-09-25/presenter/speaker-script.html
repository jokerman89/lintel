THEN

I am Johannes, the creator of Lintel. This is my personal engineering project and the journey behind it. A lintel is a horizontal support beam placed across the top of an opening—such as a door, window, or fireplace—that carries the weight of the structure above it. The name is the metaphor: useful structure supports the work. You write a detailed plan. Hours later the agent is doing something impressive, but it is no longer the thing you asked for. Or it stops and you have to reconstruct what was happening. Today I want to show the system I built around that frustration, then test where it adds value. The exchange on screen is an illustration, not a recorded benchmark. Lintel is a personal open-source project, not a Microsoft product.

04 · Meet Lintel · 2 min

The work leaves a way back.

Open this slide ↗

SAY

DO
Click through the three example steps: clarification, saved decision, fresh session. Explain who asks and who writes. Keep the registered-hook lane separate.

THEN
Why does that trail matter so much? Because each session has a limited window.

The method requires the agent to clarify material ambiguity, record consequential decisions, keep the plan current and capture evidence. Skills turn those requirements into concrete instructions; agents and local helpers perform the writes. They maintain the existing scaffolding instead of inventing a new memory store. This example begins with an export task and an unresolved date boundary. The workflow surfaces the ambiguity and the agent asks whether dates use UTC or local time. The human answers UTC. The agent records that decision, updates the task and identifies the boundary test as the next action. A compatible SessionStart hook can surface a digest, and a prompt-position hook can reassert the current step. A fresh agent still reads and checks the authoritative files before continuing. Hooks run only on exposed and registered events. A hook may warn, supply context or block selected operations, according to its actual contract; it does not itself understand every uncertainty or guarantee that a question is asked. Stop warnings do not force auto-continuation. Keep reviewed decisions and handoffs with Git; keep temporary counters and runtime ledgers ignored. The quality comes from both writing and reading the trail.

You do not need to learn nine names. Learn the shape.

Reference for questions: Lintel’s own documentation says it directly — the expensive failures in agent-driven work are correct code built against the wrong premise, discovered three hours later. SENSE reads the situation and ends with a suggested route, which is the next screen. SCOPE sizes the request and asks at most one question. DEFINE produces an approved design, not a draft. DISCOVER only reads: existing decisions, lessons and patterns. PLAN writes three files together: checkable tasks, what done means, and a brief for a fresh session. REVIEW is deliberately adversarial: spec, quality, team standards. SHIP opens a pull request by default. CAPTURE keeps lessons, a decision record and the working notes the next session picks up — the handoff — which a later DISCOVER can find; that is why it is a cycle. Every “skip it and” line is that step’s own declared cost from the documentation, not a measurement.

Claim boundaries: “at least twice” is deliberate. On a full run you are asked to confirm the route after SENSE, possibly one sizing question, then the design, the plan, and an estimate shown before BUILD — a task count and a token estimate labelled uncalibrated, never money or time. An approval gives you the chance to catch a wrong premise; it does not catch it for you. These are instructions the agent is told to follow; real enforcement is the platform’s, which is why there is no lock on this screen. “Leaves something written” does not mean committed: the situation report and the sized request are temporary working state, and a later screen draws that line. Swarming is an optional way to run PLAN, BUILD and REVIEW, not a tenth step. The strip is the illustrative opening conversation, not a measured run.

What. How. Why. Then make it compound.

First, curate durable knowledge: update an existing fact before appending another version, give lessons stable IDs, and explicitly supersede outdated lessons or decisions while preserving why they existed. Keep the memory index short and the working-state handoff current.

Second, control transient output: ignore runtime state, checkpoints, job scratch and audit churn according to the repository contract. If test evidence must survive a clone, commit the reviewed evidence deliberately. Gitignored does not mean deleted or harmless, and it is not a privacy boundary.

Third, maintain the installed kit: pin the reviewed source revision, inspect update diffs, preserve project edits and rerun the pilot. The Copilot installer uses a managed inventory and detects conflicts instead of blindly overwriting local changes. It has no general remove command. Do not delete an entire .github or .claude directory to uninstall it.

The source has memory-budget warnings and on-demand maintenance workflows, not a universal automatic garbage collector. clean recommends save/restart/restore; it cannot compact a host conversation itself. maintenance contains manual procedures and partial examples, so verify targets and retention before running them. Job-end has real promotion/cleanup behavior but is dormant by default; it is not a safe blanket cleanup switch.

Our standard should be: every durable document has a purpose, an owner and a reader. If nobody can explain who will use it next, it is probably documentation compost.

Take one recurring workflow and run the same acceptance test on the clients your team actually uses.

Before a rollout or client upgrade, record the Lintel revision, client version, enabled policies and relevant dependencies. Structural checks can show that files and schemas are valid; they cannot prove the model followed them.

One: verify actual discovery. Which instruction file, skill and agent did the client select? Check for duplicate personal and repository copies. Two: execute one bounded task with a requirement-traced plan and a real failing-then-passing acceptance check. Review the diff and evidence, not just the agent’s summary.

Four: test negative cases using synthetic fixtures: missing helper, malformed hook input, denied action, ambiguous initiative and edited managed file during update.
