Lintel is the complete company-neutral harness. The coding client executes the work. Lintel supplies reusable workflows and helper scripts, specialist role instructions, a place for plans and decisions, and a way to bring useful knowledge back into the next task.

The pack is a separate input to the method. Skills and delegated roles do the work; invoked helpers and compatible registered hooks support it. The durable records travel with the project when committed. Temporary runtime files do not.

Point at the lower platform boundary: Markdown instructions are not platform enforcement. Permissions, sandboxing and CI still belong to the host and delivery environment. Hook coverage varies by client and verified registration.

This technical map describes the inspected development snapshot. The public release may differ; the reference distinguishes public source from unreleased excerpts.

One customer case. A smaller harness.

Open this slide ↗

SAY
Core is the planned shell for a focused workflow inside the customer’s coding app.

DO
Trace the explicit start, the chosen workflow and the reviewed artifact. Use architecture review as the example.

THEN
A smaller workflow still needs to prove that it helps.

Core is the planned stripped-down version of Lintel. Start with the customer’s case and select only the context, workflow, records and checks it actually needs.

The intended interaction is explicit: a person asks to run the architecture-review workflow in the coding app they already use, including desktop GitHub Copilot. The harness helps produce a review and decision brief, with enough state to return to the work. It does not need to invoke itself automatically. That is the design intent for Core, not a claim that every host or existing full Lintel install already behaves this way.

This can avoid maintaining a separate application or hosted agent flow for a bounded, person-driven task. It still takes ownership, versioning and testing. It is not zero maintenance.

When a case needs unattended execution, shared services, durable jobs or enforced platform controls, hosted infrastructure still has a job. The question is which runtime the use case requires. Core’s distribution link will follow.

48 · Product launch · 1.25 min · optional

Does the harness earn its place?

Open this slide ↗

SAY
Benchmark should measure accepted work, including the cost of the harness.

DO
Point at what stays the same and what changes. Name the four measures. Open the prepared comparison only if time allows.

THEN
Choose one recurring task and measure the result.

The Benchmark offering is planned. Its purpose is to compare a competent baseline against the same setup with Lintel, not to compare a carefully prepared harness with a deliberately weak prompt.

Hold the model, task, project knowledge, tests and permissions constant. Change the workflow treatment. Use more than one task and independent repetitions before making a broad claim.

Measure time to an accepted change, human interventions, remaining defects and recovery, and total cost including the extra process. Bigger plans and longer answers are not success criteria by themselves. If the harness does not help a small task, that is a useful result.

The existing browser comparison is a prepared single-run exhibit available today. It is useful for inspecting artifacts and decisions, but it does not establish a general productivity gain and is not the complete Benchmark package. Its link will follow.
