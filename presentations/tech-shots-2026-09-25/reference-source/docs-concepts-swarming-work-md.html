1# Swarming work
2
3Swarming is Lintel's opt-in execution profile for an approved plan whose work can be divided into
4dependency-independent ownership domains. One coordinator dispatches bounded lanes, workers return
5attributable changes and evidence, and independent reviewers check each lane before the coordinator
6integrates it. The ordinary REVIEW phase then checks the reconciled tree.
7
8Swarming changes how PLAN, BUILD and REVIEW execute. It does not add a cycle phase, replace the
9authoritative task list, grant new permissions, or run a background scheduler.
10
11## Decide whether to swarm
12
13Use a swarm when all of these are true:
14
15- The work map is approved and contains at least two domains that can become ready independently.
16- Each worker can receive a bounded card with explicit acceptance checks.
17- Writer ownership can be expressed as non-overlapping repository-relative paths.
18- Concurrent writers can produce attributable changes in separate worktrees, patches, or an
19 equivalent host-enforced scoped sandbox. Otherwise, the same swarm may run sequentially.
20- One coordinator can own shared state, generated outputs, commits and integration.
21
22Stay with ordinary sequential BUILD when one shared file or reducer dominates, the task boundaries
23are still uncertain, or the overhead of briefs and lane reviews is larger than the work. Swarming is
24never inferred from task count; the operator opts in during PLAN or invokes `/li:swarm init` for an
25approved work map.
26
27## The committed contract
28
29A swarm adds one coordination directory beside the existing cold-executor trio:
30
31```text
32.claude/plans/<initiative>/
33├── work.json
34├── spec.md
35├── plan.md
36├── prompt.md
37└── swarm/
38 ├── coordination.json
39 ├── charter.md
40 ├── briefs/
41 │ └── <card-id>.md
42 ├── reports/
43 │ └── <card-id>.md
44 └── reviews/
45 └── <card-id>.md
46```
47
48`work.json` keeps schema version 1 and adds `execution_mode: "swarm"` plus a repository-relative
49`coordination` pointer. The mapped `tasks` artifact remains the only authority for card text,
50dependencies, status and acceptance criteria. `coordination.json` references those task IDs and
51adds execution topology only.
52
53| Artifact | Authority | Writer |
54|---|---|---|
55| mapped `tasks` artifact | Cards, dependencies, status and acceptance | Coordinator |
56| `work.json` | Artifact mapping and explicit swarm opt-in | Coordinator |
57| `coordination.json` | Waves, roles, write scopes, isolation and evidence pointers | Coordinator |
58| `charter.md` | Ownership, fan-out, fan-in and recovery rules | Coordinator |
59| `briefs/<card>.md` | Card-specific startup, scope, inputs and checks | Coordinator |
60| lane-owned paths | The implementation or documentation for one card | Assigned worker |
61| `reports/<card>.md` | Changed paths, checks, findings and limitations | Assigned worker |
62| `reviews/<card>.md` | Independent specification and quality verdict | Assigned reviewer |
63| shared ledgers, reducers, commits and integration | Reconciled initiative state | Coordinator only |
64
65A worker may write only its declared `write_scope` plus its own report. A reviewer writes only that
66lane's review. Generated catalogs, synchronized instruction blocks and other fan-in reducers stay
67coordinator-owned even when a worker edits their canonical sources.
68
69## Start and inspect a swarm
70
711. Complete PLAN and approve the mapped cards.
722. Invoke `/li:swarm init <initiative>` and review the generated charter, topology and briefs.
733. Confirm that same-wave scopes do not overlap and that every concurrent writer has an accepted
74 isolation backend.
754. Validate both the work map and the coordination contract before dispatch.
76

148## Recover without guessing
149
150Committed artifacts and attributable changes are the recovery source; chat history and worker
151process labels are not.
152
153| Situation | Recovery action |
154|---|---|
155| Worker process or local runtime state disappeared | Re-run `validate` and `status`. Preserve an attributable worktree or patch, scope-check it, then finish its report/review or replay the same brief. |
156| Partial work has no lane attribution | Do not discard or integrate it silently. Quarantine the changes, report the discrepancy, and sequence a fresh attempt after the coordinator accounts for the partial work. |
157| Worker changed an unowned path | Freeze the affected ownership domains. Narrow or reassign the scope, reconcile the isolated patch, or re-run the lane; do not hide the breach in fan-in. |
158| Lane review failed | Return findings to the same card. Later dependent waves remain blocked until a distinct reviewer records passing evidence. |
159| Two passing lanes conflict during integration | Stop integration, preserve both changes, and return to PLAN if ownership was wrong. The coordinator resolves only with an explicit, reviewed reconciliation. |
160| Independent reviewer is unavailable | Record the host limitation and leave the lane open. A self-review can inform rework but cannot manufacture independent PASS evidence. |
161
