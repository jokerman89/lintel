Lintel gives a coding agent reusable ways to understand, plan, build, review and remember work. The model, tools and permissions still come from your coding app.

Three words first.

Session

The current working conversation. A new session may load project instructions, but it does not automatically inherit the full previous conversation. Useful context needs a durable place to live.

Skill

A reusable method for a particular job: inputs, steps, expected output and checks. “Review this architecture” becomes a repeatable procedure rather than an improvised request.

Harness

The structure around the agent: workflows, context, handoffs and verification. Lintel supplies these as repository files and helpers. It does not run a hosted Lintel service.

The useful distinction

What are we building? How do we work and check it? Why did we choose this? Keep the answers available when the chat ends.

Architecture and storage · Required profile context

Agree the work. Then build it.

SENSE → SCOPE → DEFINE → DISCOVER → PLAN → BUILD → REVIEW → SHIP → CAPTURE.

Understand the request and its boundaries. Resolve the unknowns. Leave an approved plan with acceptance criteria. Build in coherent packages, verify the result, deliver within authority, and capture what should change next time.

Plans keep short, checkable leaf tasks; execution and review operate on coherent work packages. A checkbox is a useful index. It is not evidence that a test ran.

One authoritative work map

Nine phases are a map, not a tax.

A typo needs a proportionate correction and check. A cross-repository feature with policy or architecture changes needs more context, explicit decisions and stronger evidence. Keep the mandatory constraints; scale the work around the actual risk.

“Looks good” needs a receipt.

The shared Review Method defines the bounded input, applicable obligations, coverage, findings and remaining uncertainty. Review evidence must describe the content actually inspected. Changed content or a later applicable rejection invalidates an earlier pass.

MARS — Multi-Model Adversarial Review & Screening — is an optional panel over that same method. Distinct models review the same packet independently; contested claims may get a challenge round. The coordinator resolves claims against evidence, not a vote.

Use it only with operator consent and host-verifiable model selection. An incomplete panel stays incomplete. Its verdict is advisory, with release_clearance: false; REVIEW, QA and SHIP retain their own gates.

Swarm is different: parallel implementation lanes under one coordinator and one accountable plan. It needs disjoint scopes, attributable isolation and reviewed integration. If the host cannot provide those, use serial work. Self-review is not an independent reviewer.

Try one useful session.

Use a small non-production repository. Select the exact client surface, install the reviewed kit using the current adapter guide, and verify discovery. For the explicit manual route, begin with:

Read .github/lintel/START.md.
Plan a health endpoint with a focused acceptance test.
Inspect existing routes and conventions.
Do not implement until the plan is authorized.

Inspect what the agent actually loaded, the proposed scope and the acceptance check. Authorize the bounded build, review its result, then pause and resume in a fresh session. Judge the complete loop, including effort and waiting time.

Kitchen protocol v2 is a larger evaluation design, not a published victory lap. The current evidence contains no completed controlled three-arm comparison. Start with the small team pilot before scaling.
