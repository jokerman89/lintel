THE README, IN HUMAN TERMS

A repeatable working method for your coding agent.

Lintel combines repository instructions, reusable workflows, focused roles and team-specific context. Your agent carries out the work; the project retains its plans, decisions, checks and handoff.

It is an open-source project in public beta. There is no hosted Lintel service or background daemon. Markdown describes the method; local Bash and Python helpers handle installation and specific validation. Your coding client retains its existing permission model.

Three words first.

Agent

An AI model that can read your repository, edit files and run commands with the permissions you give it.

Context window

Everything the model can see at this moment: loaded instructions, your request, files it has read, tool output and the conversation so far. It is finite, and long sessions crowd older content out.

Session

One working conversation. A new session starts with an empty window. Files in the repository are what the next session can still find.

See the window fill up in the presentation

Six terms, without the mystery.

Instructions

The rules and context a session should load when it starts.

Skill

A reusable recipe for a job: for example, planning a change or reviewing it.

Agent role

A focused job description. A role is not automatically a separate or parallel worker.

Pack

The organisation’s standards, terminology, roles and reusable knowledge. The core remains company-neutral.

Project records

Plans, lessons, architecture decision records and the current handoff. An ADR explains a decision and why it was made.

Helpers

Small programs that install or check specific artifacts. A check proves only the behavior and inputs it actually exercises.

What lives where?

The presentation uses a representative Lintel layout. A tilde (~) means your user home directory. Installation routes can add host-specific files, and a project can declare a different artifact layout.

Your machine: Lintel home

~/.lintel/ holds the operator profile, installed packs, cross-repository job registry and operator audit log. The active pack, role and mode are selected through the profile. These files are machine-global; a Git clone does not install your profile or packs on a colleague’s machine.

Your coding client

The chosen host owns its settings, tool permissions and execution capabilities. ~/.claude/ is a Claude-specific client home, not the home for all coding clients. Hooks need compatible activation; merely having hook files does not mean they run.

Your project: reviewed knowledge

In the standard layout, <repo>/.claude/memory/ stores lessons and working state; .claude/decisions/ stores architecture decisions; .claude/plans/ stores plans and handoffs. The appropriate reviewed artifacts are committed and can travel with Git. A project’s declared layout and existing specification artifacts remain authoritative.

Your project: temporary runtime

<repo>/.claude/runtime/ contains temporary cycle state, job data, session saves and repository event logs. It is Git-ignored and is not part of an ordinary clone. Reviewed knowledge and handoff pointers must not depend solely on this temporary ledger.

The directory name .claude/ is a shared storage convention. It does not require Claude Code. Keep private packs, credentials and runtime churn out of shared project records; commit the appropriate reviewed project knowledge.

Client adapters can add their own files

The Copilot repository kit includes .github/copilot-instructions.md, .github/skills/li-*/SKILL.md, .github/agents/lintel-*.agent.md and resources under .github/lintel/. The skills/, agents/ and packs/ folders in Lintel’s own source bundle are not a universal installation layout copied into every customer repo.

Nine steps, three chapters.

Understand: SENSE reads the situation; SCOPE sizes the request; DEFINE makes success explicit; DISCOVER finds what already exists; PLAN makes the work checkable.

Deliver: BUILD implements; REVIEW checks the spec, quality and team standards; SHIP lands the work within the authorized scope.

Remember: CAPTURE preserves relevant lessons, decisions, working state and the handoff.

Understand, Deliver and Remember are reading aids; on screen the same three groups are labelled before any code (five of nine), code and remember. The nine phase names are Lintel’s actual workflow. Every phase declares what it produces, where you come in, and what skipping it costs; the workflow hands the decision to you at the design approval, at the plan approval, and at an estimate shown before BUILD starts. These are instructions the agent is told to follow, not locks. Smaller tasks use shorter routes. Swarming is an optional execution profile over PLAN, BUILD and REVIEW, not an additional phase.

Shorter routes.

Lintel’s documentation puts it plainly: you rarely need all nine. The first phase, SENSE, reads the request and recommends a route; you confirm it, and a mode you name yourself always wins. Before any code is touched you are shown what will run, what is skipped and a token estimate, then Proceed? [Y/n/edit].

hotfix

SENSE → BUILD → REVIEW → SHIP. The bug is known and the fix path is clear.

research-dive

SENSE → DEFINE → DISCOVER. Explore and understand; no code yet.

internal-tool

All nine, lighter REVIEW. Ordinary feature work.

meta-infra

All nine, heavier REVIEW and CAPTURE, four extra gates. The change touches the harness itself.

auto

SENSE recommends, you confirm. You are not sure which fits.

How to ask for it

Run the cycle with your request: SENSE recommends a route and you confirm it. To skip the suggestion, name the mode. In the Claude Code plugin that is /li:cycle --mode hotfix, or the shortcut that delegates to it (/li:fix; /li:research for research-dive). Routing happens when SENSE runs, that is, inside the cycle: typing a sentence to the agent without the cycle routes nothing.

You can also enter at a phase, stop early or drop one; the workflow is told to check dependencies first (BUILD needs a plan, REVIEW needs a diff, SHIP needs a passed review). Any single phase can be run on its own, which is how a hotfix can still record a lesson afterwards. Skipped phases are shown as skipped in the progress footer, so a hotfix run shows honestly that no design or plan step ran.

How the recommendation is made today: first-match keyword and path rules. “Confidence high” means a word matched, including when the match is wrong. The size check (SCOPE) can correct a route in the other direction: a request that looks like a one-line deploy but could be a large build gets exactly one clarifying question, is treated as large until you answer, and is re-routed to the full cycle only if the large reading stands and nothing is built yet. SCOPE does not run on hotfix or research-dive. The four requests on the presentation screen are illustrative; they were checked against the real matching and sizing rules at the revision below and are not recorded runs. Phrase your own requests plainly, or name the mode.

GitHub Copilot repository kit: the li-cycle skill runs the same canonical cycle, modes included. Skill names are spelled with a dash (/li-cycle, /li-plan), and the kit has no separate fix shortcut; its README example runs one phase skill directly (/li-plan …).

What does a first session look like?

  1. Choose the documented installation route for your approved coding client.
  2. Install into a pilot project and run the relevant installation checks.
  3. Ask for one small change. The README uses a health endpoint with a focused acceptance test.
  4. Inspect the plan; execute within the scope you have authorized.
  5. Read the verification and handoff. Try resuming from a fresh session.

In the Copilot repository kit, the planning example is /li-plan Add a health endpoint with a focused acceptance test. Other hosts can expose different names. Existing Spec Kit artifacts can remain authoritative; the integration is designed to avoid creating competing plans.

Where the deeper workflows fit.

The catalog includes architecture, data, security, operations, testing, design and document workflows. Use these when the problem needs them. For a small change, a short plan and proportionate verification can be enough.
