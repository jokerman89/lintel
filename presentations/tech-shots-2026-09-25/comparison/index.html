Menu, Orders, Inventory and Reports. A usable operations app with exact cents, basket, checkout, stock, persistence, CSV, mobile layout and keyboard access.

One prompt. Verbatim.

All arms receive identical prompt, brief, fixture, selectors and starter bytes. The frozen brief supplies the requirements; the prompt deliberately forbids follow-up questions.

Build the complete Service House kitchen operations website specified in BRIEF.md, using the supplied fixture.json and selectors.json contracts. Satisfy every numbered requirement, including error handling, persistence, mobile layout and keyboard access. Build the real working interactions, not screenshots or placeholders. Use the workflow configured in this workspace, preserve the public contracts and do not access sibling workspaces, benchmark graders, reference solutions or previous results. Do not install additional agent workflows. Start the website with npm start using the PORT environment variable, keep it running, verify the result, and report completion only when it is usable. Do not ask follow-up questions; make reasonable implementation decisions within the brief.

32 checks. 100 possible points.

K16 and K25 weigh five points; all others weigh three. The score covers these observable behaviors, not complete security, accessibility certification or subjective design quality.

IDRequired behavior
K01The app loads with a visible Service House heading and no uncaught browser errors.
K02Four accessible navigation controls switch between Menu, Orders, Inventory and Reports without leaving the app.
K03Menu initially displays all six fixture dishes with the correct names.
K04Search is case-insensitive, trims outer whitespace, matches dish names, and clearing restores matching items.
K05The category select has values `all`, `starters`, `mains`, `drinks` and filters correctly.
K06The Vegan only checkbox filters out bread and pasta; search, category and vegan filters combine with AND.
K07Zero-stock pasta is visibly Sold out and its add control is disabled; the other dishes can be added.
K08Every dish displays its exact fixture price with two decimal places.
K09Adding a dish creates one basket row; repeated adds increment that row rather than duplicating it.
K10Basket quantity is an editable integer from 1 to available stock (maximum 20); zero, negative, fractional, nonnumeric and excess values cannot produce an invalid order. Invalid edits leave the last valid quantity and display a visible error.
K11Removing a basket row removes its contribution; removing the last row shows a meaningful empty basket.
K12Subtotal is the sum of each price times quantity, without floating-point currency drift.
K13Applying `KITCHEN10` discounts subtotal by 10%, rounded to the nearest cent. An invalid code shows `discount-error` and clears the discount; applying an empty code clears it without an error.
K14Tax is 10% of discounted subtotal, rounded to nearest cent; total is discounted subtotal plus tax. Two soups and a lemonade with KITCHEN10 total $21.29 (subtotal $21.50, discount $2.15, tax $1.94).
K15Checkout rejects an empty basket, a blank/whitespace customer name, and tables outside integer 1-30. It shows an actionable `checkout-error` and creates no ticket.
K16A valid checkout creates exactly one queued ticket, with sequential ID T001 onward, customer, table, dish quantities and correct total; basket and discount are cleared.
K17Optional order notes are displayed verbatim as text on the ticket, never interpreted as HTML. Customer names must also be rendered as text.
K18A queued ticket has Start cooking; clicking it moves to cooking and offers Mark ready. Status is visible and exposed in `data-status`.
K19Mark ready moves cooking to ready. Ready/cancelled tickets have no enabled advance or cancel action.
K20Queued or cooking tickets can be cancelled exactly once, remain visible as cancelled, and restore their reserved stock exactly once.
K21Stock is reserved only on successful checkout, not when adding to the basket. Inventory and Menu stock agree after submission.
K22An order cannot exceed current stock. Ordering all eight soups makes soup Sold out; no ninth soup can be ordered until restocked/cancelled.
K23Inventory shows all six stock counts; a labeled restock input per item adds an integer 1-99. Zero, negative, fractional and over-99 amounts show `stock-error` without changing stock.
K24Each dish exposes its allergens as text, or explicitly None. Vegan status is visible, not color-only.
K25A reload preserves orders, statuses, stock and basket; a completed checkout is not duplicated. Store client state locally.
K26Reports show noncancelled order count, cancelled count and revenue from ready tickets only. Cancelled/queued/cooking tickets contribute no revenue.
K27Export CSV downloads all tickets with header `ticket,customer,table,status,total`; total is decimal dollars without a currency sign. Escape quotes, commas and newlines correctly.
K28An unmatched menu search and a fresh Orders view show clear empty states, not blank space or an error.
K29Theme toggle switches `document.documentElement.dataset.theme` between `light` and `dark`, visibly changes colors, and survives reload.
K30At a 390x844 viewport there is no horizontal document overflow; navigation, basket and checkout remain reachable and usable.
K31Navigation, search, quantity/checkout/restock inputs and buttons have accessible names; native keyboard focus is visible and controls work without a pointer.
K32Reset demo requires confirmation through a visible `confirm-reset` button. Cancelling leaves state intact; confirming restores fixture stock, empty orders/basket and zero report values.

A fair test can disappoint you.

  • Freeze source, prompt, brief, fixtures, starter, grader, model configuration, permissions and time limits before the run.
  • Keep the grader, reference solution, previous results and other candidates outside the candidate workspace.
  • Inspect actual host discovery. User-global instructions can contaminate the naked arm; repository separation alone is not a sandbox.
  • Run arms sequentially and counterbalance order across at least three independent repetitions. Simultaneous windows are a noncontrolled showcase.
  • Naked versus Lintel compares workflow plus delegate-model configuration. The two Lintel arms retain the same delegate models and review policy. Add an all-same-model series to isolate model mix further.
  • Record actual active implementation overlap to establish swarming. Session lifetimes or parallel review sessions alone do not prove it.
  • Retain failures, timeouts, exclusions and every grading attempt. Never repair an app after the stop boundary and keep its old completion time.
