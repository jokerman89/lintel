# Advice mode

Use `/frontend-design --mode advice <question>` for a design-system decision before
implementation. No code or rendered artifact is generated by this mode.
For built UI use `/frontend-design-review`; for a concrete sketch use
`/generate-web --mode mockup`; for a plan use `/inspect --target plan --lens design`.

## Inputs

- The question or proposal, inline or an explicitly selected local file.
- `--scope <area>` limits the surface under discussion.
- `--read-design-system <dir>` selects project design-system documentation.
  Otherwise use the repository's declared design-system location and closest
  existing components. Do not scan a personal vault or assume a product-specific
  directory layout.
- `--cross-check` requests the separate `/cross-check` workflow. Actual
  independence requires a different attributable actor through a permitted host
  operation; a second role label in this context is not an outside opinion.

## Procedure

1. State the decision and its constraints. Separate the user task, aesthetic
   preference, accessibility requirements and implementation scope.
2. Read relevant tokens, design-system documentation, existing components and
   observed usage. Use the director's verified profile and design-DNA retrieval
   when comparing new choices. Cite the files and distinguish observed facts
   from assumptions; do not invent usage counts or performance measurements.
3. Give three viable alternatives where they exist. For each, name the design
   move, existing tokens/utilities to reuse, implementation cost, regression risk,
   upside and downside. Include responsive behavior, keyboard/focus, reduced
   motion and migration impact where relevant. If only two options are honest,
   say so rather than manufacture a third.
4. Recommend one with a reason tied to the question and evidence. Explain what
   new fact would change the recommendation. The operator still owns the choice;
   advice does not authorize a token migration or implementation.
5. If requested and available, obtain the independent cross-check of the same
   question, alternatives and sources. Attribute its actual result separately.
   If unavailable or denied, keep the local recommendation and disclose that
   independent advice remains unverified; do not retry through another surface.
6. Return Markdown with question, context read, alternatives/trade-offs,
   recommendation, assumptions and the separate cross-check result, if any.
   File output requires an explicit owned `--out`; otherwise return the advice.

## Boundaries

Missing required profile/tokens block the affected recommendation. Missing optional
design documentation lowers confidence and stays explicit. Resolve a genuinely
ambiguous decision through the actual question tool; never pick a materially
different scope solely because the host lacks a particular tool.

Use sanitized examples. Customer copy is judged against the selected pack's
actual voice requirements, not rewritten or distributed here. A recommendation
can feed design mode, variants mode or mockup rendering only within authorization.
