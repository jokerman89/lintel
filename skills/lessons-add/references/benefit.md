# Lesson benefit and recurrence

CAPTURE and lessons-add use this reasoning before add/update/supersede/no-op.
Read the full related lesson and the selected work's actual correction/evidence;
keyword-hit ranking is retrieval, not usefulness or usage measurement.

- **Observed benefit:** was this rule actually applied in later work? Name the
  dated instance, what decision changed and the observed outcome/evidence. Separate
  an avoided repeat that can be supported from a plausible benefit or a causal guess.
- **Recurrence:** did the same failure recur after the rule existed? Was the rule
  unavailable, missed, inapplicable, ambiguous, contradicted or followed but ineffective?
  Cite the occurrence rather than treating another reference as success.
- **Unknown:** if no later application or comparable outcome is observed, say
  benefit/recurrence unknown. A new lesson, silence, a green fixture or an empty
  incident log is not proof of prevention. State what future observation would help.

Use this to choose an existing operation: no-op when the rule already covers the
case; update to clarify a demonstrated gap; supersede a contradicted/obsolete rule;
add only genuinely new durable guidance. Propose merging overlapping lessons or
retiring obsolete guidance through the existing update/supersession path, preserving
IDs/history and obtaining the owner's authority. Do not delete old blocks or invent
a bulk retirement writer.

Keep this reasoning as brief prose in the existing Rule / Why / How to apply body
or the authorized capture report. No schema, reference counter, efficacy score,
automatic calibration or automatic promotion is added. Promotion additionally needs
observed applicability beyond this repository and an explicit destination/consent;
unknown benefit is a reason to defer, not manufacture evidence.
