# Design: CLAUDE.md as a capability + memory surface (not just a rulebook)

Generated by /office-hours on 2026-06-05
Branch: v4.8-dogfood-scaffolding
Repo: jokerman89/lintel
Status: APPROVED
Mode: Builder (internal tooling)

## Problem statement

Lintel ships a deep memory + capability system — `tasks/lessons.md`, `tasks/memory.md`,
`tasks/personas.md`, `docs/adr/`, `.lintel/state/`, `~/.lintel/profile.yaml`, the 8-phase
cycle, context-warming, jobs, roles, knowhow — but its CLAUDE.md is a rulebook that barely
surfaces any of it. The operator's worry, verbatim: it's embarrassing to miss basics we think
Lintel can do but that never become real because CLAUDE.md doesn't show them.

## The key insight (what's auto-loaded vs not)

Claude Code auto-loads a specific set; the rest is invisible until something reads it.

**Auto-loaded (no CLAUDE.md help needed):**
- `CLAUDE.md` (repo + global) — in context every session.
- **Skills** — names + descriptions are surfaced; the Skill tool invokes them. Lintel's 165
  skills are *discoverable* automatically. A hand-typed routing map is mostly redundant for
  discovery; it only nudges *proactive* firing.
- `.claude/agents/` subagents — available to the Task tool.
- **Hooks** — run automatically on events.

**NOT auto-loaded (the real gap):**
- `tasks/lessons.md`, `tasks/memory.md`, `tasks/personas.md`, `~/.lintel/profile.yaml`,
  `.lintel/state/`, `docs/adr/` — plain files. Read only if CLAUDE.md instructs, a hook
  injects, or the user asks.

**Therefore:** the snowball did not compound because the *memory files were never auto-read*,
not because skills were hidden. The operator's own global memory works precisely because the
harness injects a `MEMORY.md` index every session. Lintel has no equivalent auto-load.

This directly answers the three questions asked:
- *What does Lintel assume that CLAUDE.md omits?* That its lessons/memory/personas/profile/state
  reach the session. They don't. Plus: the cycle as primary workflow, context-warming, jobs,
  roles — all invisible.
- *What's missing vs the example CLAUDE.md?* A skill-routing nudge; the structured-comment
  format (template has it, the current root CLAUDE.md dropped it); a session-start that reads
  the profile.
- *What to do better?* Make CLAUDE.md a capability + memory map and add a mechanical auto-load
  for the snowball.

## Premises (agreed)

1. Fix targets the not-auto-loaded set, not skill discovery.
2. Auto-load must be mechanical (a hook), not a soft "please read these files."
3. SessionStart hooks are Claude-Code-specific → the template needs a CLAUDE.md-ritual fallback
   for non-hook CLIs.
4. Ships in both Lintel's own repo and the scaffolded template.
5. Skill routing stays a light nudge, not a generated map.

## Approaches considered

- **A — SessionStart digest hook (CHOSEN).** A hook reads the snowball + active profile and
  injects a compact digest into context every session. True auto-load, mirrors global MEMORY.md.
- **B — CLAUDE.md instruction only.** Session-start ritual says "read these files." Rejected:
  relies on the agent obeying every time and costs full-file context each session — the soft
  version that already silently failed.
- **C — Index-file pattern (tasks/INDEX.md).** A tiny always-read index. Rejected as primary
  (still relies on being read), but adopted as the digest's *content model*: the hook emits an
  index-style digest, not full files.

## Recommended approach: SessionStart digest hook + a leaner, capability-aware CLAUDE.md

### 1. The digest hook (primary, Claude Code)

A new hook, `hooks/shared/session-digest/`, wired as a **SessionStart** hook. It emits a compact
digest (target ≤ ~400 tokens) as `additionalContext`:

```
LINTEL SESSION DIGEST
Active pack: <profile active_pack> · mode: <default_mode> · role: <role_active|none>
Compliance: <resolve_pack_field compliance.mode>
Recent lessons (last N): L-006 dogfood-the-factory · L-005 grep-completeness · …
Memory highlights: <top lines of tasks/memory.md>
Open jobs: <~/.lintel/jobs/_active.md count + names>
Recent decisions: ADR-0001 dogfooding · <latest structure-changes slug>
Pending migrations: <docs/v4.x/migrations count, if any>
```

- Reads: `~/.lintel/profile.yaml`, `tasks/lessons.md` (tail/index), `tasks/memory.md`,
  `~/.lintel/jobs/_active.md`, `docs/adr/` titles, `docs/v4.x/migrations/`.
- Cheap: emits an index/digest, never full files. Degrades silently if a source is absent
  (works in a fresh scaffolded repo with empty lessons).
- Inert until the operator opts in (symlink/settings, per Lintel's hook convention) — but the
  installer/`li-scaffold` wires it by default for new repos.

### 2. CLAUDE.md changes (both Lintel root + template)

- **Skill routing (light nudge).** A short `## Skill routing` section: "When a request matches a
  skill, invoke it. Cycle work → `/li:cycle`; bug → `/li:investigate`; tests → `/li:qa`; deep
  context → `/li:context-warm`; decision → `/adr-new`; discover all → `/li:catalog`." A nudge,
  not a maintained map.
- **Where state lives (the memory map).** A `## Where state lives` section naming each store and
  its purpose (lessons/memory/personas/ADRs/`.lintel/state`/profile/jobs) so the agent knows
  what to read on demand and where to write the snowball.
- **Session-start ritual = fallback.** Keep the ritual list (read lessons/memory/personas/profile)
  as the non-hook-CLI fallback, explicitly labelled: "Claude Code gets this via the session-digest
  hook; other CLIs read these here."
- **Restore the structured-comment format** (`component/implements/intent/constraints`) dropped
  from the current root CLAUDE.md.
- **Cycle as the primary workflow** — state plainly that `/li:cycle` (SENSE→CAPTURE) is the
  default work loop and writes `.lintel/state/00-state.md`.

### 3. Template + dogfood parity

`scaffolding/01-foundation/` ships the hook + the CLAUDE.md sections, so every scaffolded repo
gets auto-loaded memory + capability surfacing. Lintel's own root adopts the same (continues the
v4.8 dogfooding).

## Open questions

- Digest token budget: ~400 default; pack-overridable? (lean yes, via `navigation.*` or a new
  `digest.budget_tokens`.)
- Should the digest include the last N lessons by recency, or by keyword-relevance to the cwd diff
  (more useful, more cost)? Start recency; add relevance later.
- Unify ADR location: Lintel uses `docs/adr/`; deeplex uses `docs/06-decisions/`. Pick one for the
  template (recommend `docs/adr/`).

## Success criteria

- A fresh Claude Code session in a Lintel-scaffolded repo shows the digest (pack/mode/role +
  recent lessons + open jobs) without being asked.
- `li-doctor` reports the session-digest hook present + wired.
- The snowball demonstrably reaches the session: ask "what were the recent lessons?" at session
  start and the answer is correct with zero prior reads.

## Distribution / how it ships

- Hook lives in `hooks/shared/session-digest/` (HOOK.md + run.sh), wired via `install/` +
  `li-scaffold` (Claude Code settings.json SessionStart entry). Other CLIs fall back to the
  CLAUDE.md ritual.
- `bin/li-doctor` gains a check: "session-digest hook wired?".
