## Problem Statement

JStack v1 shipped: 65 skills, 40 agents, 14 hooks, T0 corpus populated, install + verify + CI matrix landed (commit `a0c996c`). It works. It's "snygg." But three structural gaps remain before it earns the role it was actually built for — being the operator's MS-CAIP-SE toolchain on every engagement, on every CLI, at every context-window size:

1. **Naming gap.** Tools carry generic engineering vocab (`/qa`, `/review`, `/ship`) instead of MS-internal process language (1ES, 1ESPT, OneBranch, EV2, SDL, SFI, 1CS). The operator's mental model is MS; the toolchain should mirror that, not force re-translation every session.

2. **Portability gap.** Skills declare `cli_support: [...]` but there's no runtime that ENFORCES degradation cleanly across claude-code, GHCP CLI, GHCP App, and Codex. A skill marked `cli_support: [claude-code]` runs perfectly there but produces silent confusion (or failure) elsewhere. We need graceful degradation as a first-class mechanism, not a frontmatter assertion.

3. **Context gap.** Today's runtime treats context as "what fits before compaction." For hard CAIP-SE engagements — multi-week customer demos, parallel decomposed tasks, warmup-heavy integration moments — we need explicit context-budgeting. 1M context as a usable RESOURCE, not a default cap. Outcome-based: spend tokens where outcome density is highest, not save tokens for the sake of saving.

4. **Deliverable gap.** CAIP-SE engagements produce customer-bound artifacts: pitch PPTs, technical Word docs, demo web pages. Today these are produced by hand or via generic tools that don't carry MS brand guides, Azure asset library, latest Trailblazer copy patterns, or CAIP-SE-tier quality conventions. The operator does this work manually every engagement. It compounds across deliverables.

V2 closes all four gaps in one ship cycle (Big Bang per the operator's call). T0 voice calibration runs as part of v2.0 so customer-bound doc generation inherits CALIBRATED voice from day one.

## What Makes This Cool

The thing that doesn't exist anywhere else: **a CAIP-SE engagement-shaped toolchain where every skill speaks MS process language, every output carries MS brand, every CLI works (or degrades honestly), and 1M context is a budgeted resource not a survival problem.**

gstack is universal. GSD is methodology. Speckit is spec-first. Superpowers is plugin-shaped. Each is opinionated but none is engagement-shaped for the specific work CAIP-SE does: customer-facing AI architecture engagements where the deliverable is a PPT a CISO will read, a Word doc a CAIP-SE-tier engagement summary will land in, and a web demo that has to feel like Azure ten seconds in.

JStack v2 isn't trying to be the best general-purpose harness. It's trying to be the best harness for one specific shape of work: CAIP-SE engagements, end-to-end, with MS as the only context that matters. That niche is the moat.

A second cool thing: the **1M context engine isn't a token-bag**. It's a context-budgeting framework with explicit warmup patterns. Hard phases can deliberately preload reference material, code context, customer-engagement metadata, design assets — and the engine knows when to drain, when to checkpoint, when to compress. The operator stops thinking about "am I close to compaction?" and starts thinking about "what's the highest-leverage thing to load right now?"

## Constraints

**Operator-stated, non-negotiable:**

- CAIP-SE engagement focus. Generic features that don't serve a CAIP-SE workflow are out-of-scope (or moved to Layer 4 power-user).
- MS-internal terminology must mirror real process (1ES, 1ESPT, OneBranch, EV2, SDL, SFI, 1CS, etc.). See "Naming Migration Plan" below.
- No customer data in repo, prompts, or generated artifacts. Layer 2 5-always-on rules + 2 BLOCK hooks stay enforced.
- License posture: MIT for operator-authored content. Permissive bundling only into MS-internal MIT repos. Restricted-tier upstreams stay install-only.
- gstack IP reuse is approved (per operator); attribution where applicable, but no copy-paste of restricted-license content into MS-internal bundles.

**Performance / technical:**

- 1M context as upper bound, not default. Phases declare their context budget; engine enforces.
- Outcome-based optimization: token spend is acceptable where outcome density is high. Token saving is acceptable where it doesn't compromise outcome.
- Cross-CLI: claude-code (full), Codex (degraded but functional for ≥80% of skills), GHCP CLI (functional ≥60%), GHCP App (functional ≥60%). Per `cli_support` frontmatter, runtime shim where mechanically possible.
- Heavy surface, lightweight implementation: each individual skill stays ≤300 lines. Aggregate complexity surfaces in the engine, not in any single skill.

**Compliance / governance:**

- All v1 compliance gates (5 always-on, 7 on-demand, 8 reference docs) remain.
- New addition: AGT (Agent Governance Framework) terminology adoption. Existing 5-level precedence model maps to AGT identity model.
- New addition: SDL emerging-practices integration. AI Risk Assessment, AI Memory Protections, MCP server security, XPIA/UPIA patterns surface in relevant skills.

## Premises

These premises shape v2 architecture decisions. The operator confirmed via approach choice (Big Bang v2.0 + T0 calibration). Premises that were challenged in office-hours are recorded with their refined form.

**P1 — Niche over universal (refined).**
Original: "En harness som gör allt, bättre än gstack/GSD/speckit/superpowers."
Refined: "Best for CAIP-SE engagement workflows specifically. Not universal." The "does everything" framing leads to bloat. Niche-shaped excellence is the moat.

**P2 — Graceful degradation, not 100% portability (refined).**
Original: "100% portabilitet till alla CLI."
Refined: "Graceful degradation per skill via cli_support frontmatter + runtime shim where mechanically possible. ~80% portability with honesty about the 20%." Some skills inherently can't be portable (browser-dependent, Agent-tool-dependent). Honesty beats hype.

**P3 — Context budgeting, not raw 1M (refined).**
Original: "1M context window för tuffa faser."
Refined: "Context-budgeting per task-decomposition. 1M as resource upper bound, not default state." Throwing 1M tokens at Claude doesn't make Claude smarter; it gives Claude more to be distracted by. The engine is the value, not the size.

**P4 — Brand-compliant doc-gen, not "better than PPT" (refined).**
Original: "PPT bättre än MS original."
Refined: "Brand-compliant doc generation matching CAIP-SE customer-bound quality bar. Latest MS brand guides + Azure assets + Trailblazer-voice copy." PowerPoint as a product has decades of research; we're not beating it. We're shipping artifacts that carry MS brand identity correctly + are tuned for CAIP-SE customer audiences.

**P5 — MS-internal terminology adoption (accepted).**
1ES, 1ESPT, OneBranch, EV2, SDL, SFI, 1CS, AGT, RAIS, DSB, DPIA, Liquid, S360, ServiceTree become first-class vocabulary. Mirrors the operator's actual mental model. Lock-in to MS-internal is acceptable — this IS an internal tool.

**P6 — Self-maintenance with explicit watcher mechanism (accepted with detail).**
Outcome-based optimization is correct. The mechanism: explicit watchers (context-tokenwatch, engagement-watcher, voice-staleness-watcher, etc.) + operator-tunable thresholds + manual `/clean` override + audit log per Layer 4 power-user pattern. Same model as v1 but instrumented across more dimensions.

## Approaches Considered

### Approach A: Lean + Layered (rejected by operator)
v2.0 = MS-naming + portability shim. v2.1 = 1M context-budget engine. v2.2 = MS-proprietary doc-generation. v2.3 = adoption polish.
Pro: each reversible, each independently shippable, lower bloat risk.
Con: PPT skill lands in v2.2 not v2.0 — slower to "have everything."

### Approach B: Maximal Big Bang v2.0 (chosen)
All four expansions land in one release. PPT, Word, Web, MS-naming, 1M context-budgeting, portability shim, T0 calibration.
Pro: "Done" is actually done. One review-cycle, one ship-gate. Operator stops carrying scope-future across multiple weeks.
Con: Same bloat trap that gstack/speckit/superpowers fell into. Mitigation: hard scope-control + per-component spec discipline + Phase 8-style ship gate before tag.

### Approach C: Strip + Rebuild (rejected)
Reduce v1 from 65 skills to 30 essential. Rebuild from leaner core. Add v2 expansions on top.
Pro: leanest long-term, forces honest re-evaluation.
Con: throws away 24 hours of v1 momentum + working infrastructure that's already shipping value.

## Recommended Approach: B — Maximal Big Bang v2.0

The operator's choice. This design covers ALL four expansions plus T0 calibration as a single ship cycle.

Critical mitigation: **scope is sealed BEFORE build begins.** This design document IS the scope. New skills/features outside this design are deferred to v2.1, not added mid-build. The bloat trap is real; the only defense is a sealed scope contract.

#### Component 2: Portability Shim Runtime

Goal: Every skill declares `cli_support` in frontmatter; runtime enforces graceful degradation per CLI.

**(P1 fix T2 — eng-review):** Phase B sub-step 0 is CLI fingerprinting. Without reliable CLI detection, every shim decision is guessed. Build detection FIRST, then the shim layer on top.

**Step 0: CLI fingerprinting (before any shim logic):**

Detection strategy (cascading; first match wins):
1. **Explicit env var** — `JSTACK_CLI` (operator can pin via config or shell init)
2. **Process inspection** — `process.argv0` / `$0` for known binary names (`claude-code`, `codex`, `gh-copilot`)
3. **Tool-availability probe** — check for CLI-specific tools/env-vars (e.g. `CLAUDE_CODE_*` env vars, `CODEX_*`, `GH_TOKEN` + `gh copilot` subcommand availability)
4. **Operator-declared fallback** — `~/.jstack/cli-id.txt` written by operator if auto-detection fails
5. **Last resort** — refuse to run + ask operator: "Could not detect CLI. Set JSTACK_CLI env var or write CLI ID to ~/.jstack/cli-id.txt and retry."

Detection runs once per session, cached in `~/.jstack/sessions/$SESSION_ID/cli-id.txt`. Subsequent skill invocations read the cache.

**Shim mechanism (after fingerprinting succeeds):**

1. **Skill invocation interceptor**: Before any skill body runs, the runtime checks the detected CLI against the skill's `cli_support` array.

2. **Per-CLI behavior:**
   - **Full support:** skill runs unchanged.
   - **Degraded support:** skill runs with shim overlay (specific to each skill — see "Per-CLI degradation map" below).
   - **Not supported:** skill refuses to run, surfaces "this skill is `claude-code` only" + suggests nearest-equivalent skill that DOES support current CLI.

3. **AskUserQuestion shim:**
   - claude-code: native AskUserQuestion or MCP variant.
   - Codex: NON-INTERACTIVE mode — `codex exec` cannot block on stdin. Shim auto-picks the `(recommended)` option declared in the AskUserQuestion call. Surfaces `[auto-picked recommended: <label>]` in output. Operator can re-run with `--manual-decisions` flag to receive a list of decisions made + override. **(P1 fix T7 — eng-review)**
   - GHCP CLI / App: synthesize prompts as numbered list in chat; user replies with number.

4. **Agent tool shim:**
   - claude-code: native Agent tool (Task tool).
   - Codex: spawn `codex exec` subprocess with focused prompt.
   - GHCP CLI / App: NOT SUPPORTED (no equivalent). Skills using Agent tool decline to run.

5. **Browser tool shim:**
   - claude-code: managed Chromium via /browse.
   - All others: skill refuses; surfaces manual-browse workaround.

**Per-CLI degradation map** (per skill, declared in frontmatter):

```yaml
cli_support:
  - cli: claude-code
    level: full
  - cli: codex
    level: degraded
    degradation:
      - AskUserQuestion → sequential-prompt
      - Agent → codex-exec-subprocess
  - cli: copilot-cli
    level: not-supported
    reason: requires Agent tool, no Codex shim available
```

**Skills that change cli_support in v2:**

Most skills already declare `cli_support: [claude-code, codex]`. v2 adds runtime enforcement + the degradation map. About 15 skills declare degradation behaviors specific to their workflow (planning skills, voice gates, doc-gen).

About 8 skills stay `cli_support: [claude-code]` only due to hard dependencies (browser, design-binary). These skills get the "this is claude-code only" surface treatment with nearest-equivalent recommendation.

#### Component 3: 1M Context Budget Engine

Goal: Context as a budgeted resource per task-phase, not as "what fits before compaction."

**(P1 fix T1 — eng-review):** v2.0 ships engine as **declarative + soft-enforcement only**. The engine emits warnings at 80% and 100% of budget — operator decides next move. Hard enforcement (block on budget exceeded) deferred to v2.0.5 patch AFTER usage data confirms warnings get acted on. Boring-by-default applied to a novel system; Claude can't compact mid-session anyway so hard enforcement would mostly produce "override" decisions which is decorative.

**(P1 fix T10 — eng-review):** Error semantics specified in [CONTEXT-ENGINE.md](../../CONTEXT-ENGINE.md):
- Phase transition error → log + continue current phase (don't crash)
- Budget-exceeded mid-phase → warn + offer compress/checkpoint/override
- Operator-cancel → checkpoint current phase state + persist to `~/.jstack/sessions/$SESSION_ID/checkpoint-{phase}.md`
- Engine read error on config → fall back to safe defaults (200k budget) + warn

**Engine design:**

1. **Phase declaration**: Skills + multi-step orchestrators declare context-budget per phase:
   ```yaml
   ---
   name: jstack-engagement-deepdive
   context_phases:
     - phase: preload
       budget: 200k
       warmup_tasks: ["read all engagement docs", "summarize prior sessions"]
     - phase: build
       budget: 500k
       reserve_for_eval: 100k
     - phase: voice_check
       budget: 150k
       reserve_for_corpus_calibration: 50k
   ---
   ```

2. **Warmup-task pattern**: Heavy phases EXPLICITLY preload context with high-leverage material at start. The engine charges this against phase budget; it's a deliberate investment, not waste.

3. **Budget enforcement**: When phase budget is reached, the engine surfaces:
   - "Phase budget consumed (500k of 500k). Options: (a) compress + continue, (b) checkpoint + switch phase, (c) override budget +N tokens."
   - Operator picks. Audit-logged. NO silent compaction.

4. **Cross-phase decay**: When transitioning between phases, the engine offers structured cleanup — what to keep, what to summarize-then-drop, what to fully drop. Operator confirms or auto-decides per `decay_policy` in config.

5. **Outcome-based scoring**: Each phase logs (in audit) tokens spent + outcome shipped. Periodic `/perfbench --context` report shows where token spend correlates to outcome density, where not.

**New skills introduced:**

- `/context-budget` — view + modify current phase budget, declare new phase, checkpoint.
- `/context-warmup` — explicit preload of high-leverage context per declared warmup pattern.
- `/context-budgetwatch` (renames `/context-tokenwatch`) — passive monitoring with budget-aware thresholds.
- Agent: `ContextBudgetAdvisor` — Layer 4 agent that suggests phase declarations for unstructured tasks.

**Config:**

```yaml
# ~/.jstack/config.yaml v2
context:
  enabled: true                    # opt-in; off = use claude-code default
  default_budget: 200000           # safe default
  max_budget: 1000000              # 1M ceiling
  perf_mode_budget: 800000         # /perf-mode invocation default
  decay_policy: prompt             # prompt | aggressive | conservative
  warmup_enabled: true
  outcome_logging: true
watchers:
  budget_soft_pct: 80              # warn at 80% of phase budget
  budget_hard_pct: 100             # block at 100%
  staleness_days_calibration: 30
  staleness_days_engagement: 14
```

#### Component 4: MS-Proprietary Doc Generation

Goal: Customer-bound deliverables that carry MS brand + Azure assets + Trailblazer voice, at CAIP-SE-tier quality.

**Doc-gen skill set (new in v2):**

1. **`/generate-ppt`** — produce branded PowerPoint deck from a brief + supporting data.
   - Reads `~/.jstack/brand/ppt-templates/` (latest MS brand guides — operator maintains).
   - Pulls from `~/.jstack/brand/azure-assets/` (Azure service icons + diagram primitives — operator maintains).
   - Uses pptx-genjs (or similar) under the hood to produce actual .pptx files (not just outlines).
   - Voice tier: `mixed` — internal scaffolding for slide structure, trailblazer for customer-bound copy.
   - Output: DRAFT .pptx + a parallel `meta.yaml` declaring provenance + voice-check status.
   - Gated: `/rais-customer-voice-check` MUST pass before file moves out of `~/.jstack/draft/`.

2. **`/generate-word`** — produce branded Word doc (technical deliverable, engagement summary, transparency note, etc.).
   - Reads `~/.jstack/brand/word-templates/`.
   - Uses docx-templater under the hood.
   - Voice tier per `--target`: technical (internal voice) / customer-summary (trailblazer) / transparency-note (trailblazer with extra honest-limitations check).
   - Output: DRAFT .docx + meta.yaml.
   - Gated as above.

3. **`/generate-web`** — produce static demo web page or landing scaffolding.
   - Reads `~/.jstack/brand/web-templates/` (Lovable-style modern aesthetic + Azure icon library + Trailblazer copy patterns).
   - Output: single-file HTML or multi-file Next.js scaffold.
   - Voice tier: mixed.
   - Gated as above.

4. **`/brand-update`** — refresh `~/.jstack/brand/` from MS brand portal (manual operator pull; verifies signatures and versions).

5. **`/asset-search`** — search `~/.jstack/brand/azure-assets/` for the right icon / diagram primitive for a use case.

**(P1 fix T3 — eng-review): Minimal default templates fallback**

Ship in-repo at `scaffolding/03-personal-advanced/doc-gen/default-templates/`:
- `default-ppt-template.json` — generic styling (system font, neutral palette, no MS brand)
- `default-word-template.json` — same generic baseline
- `default-web-template.html` — minimal modern aesthetic baseline

When `~/.jstack/brand/<type>-templates/` is empty or missing, doc-gen falls back to defaults + marks output with `brand_version: default-fallback` in meta.yaml. This unblocks doc-gen runtime regardless of brand-acquisition status; operator pulls real brand later and fallback drops away.

**Library choice (P1 fix T6 — eng-review):** Locked in design:
- PPT: `pptx-genjs` (TypeScript-native, repo stack consistency)
- Word: `docx-templater`
- Web: native HTML/Next.js (no external lib needed for generation)

**Agents introduced for doc-gen:**

- **`PPTNarrativeArchitect`** (Layer 3, permissive) — designs slide arc + per-slide content goal before generation.
- **`WordTechnicalEditor`** (Layer 3, permissive) — reviews technical Word output for accuracy + voice + structure.
- **`WebExperienceCritic`** (Layer 3, permissive) — applies 6-pillar critique to generated web output.

**Quality bar:**

Doc-gen output must pass FOUR gates before it's distributable:

1. `/rais-customer-voice-check` (Trailblazer voice rubric, ≥85 score, 0 P1 violations)
2. Brand-conformance check (template matches latest brand guide; assets are current; no unauthorized branding)
3. Honest-limitations check (transparency notes only — limitations ≥ capabilities − 2)
4. `/provenance-track` record produced (source chain + voice-check status + brand version)

All four gates wired into `/release-ev2` (formerly `/ship`). Customer-bound artifacts cannot ship without passing all four.

#### Component 5: T0 Voice Calibration (in scope per operator)

Goal: Trailblazer corpus calibrated to ≥90% per-cell accuracy, ≥10 cells PASS, before v2.0 tag.

**Calibration plan:**

1. **First eval run**: Run `/jstack-eval` against current corpus (60 paragraphs, 12 cells). Capture per-cell accuracy.
2. **Rubric iteration**: For any cell <90% accuracy, refine `TRAILBLAZER-TEST.md` rubric — sharpen the technique definition, add explicit fail-mode tells, adjust scoring weights.
3. **Re-eval until target met**: Iterate 1-3 times. If a cell persists below 90% after 3 iterations, drop it from v1 scope (operator decision; cells P1 Vulnerability and R4 Dream are most likely candidates per known difficulty).
4. **CALIBRATED stamp**: When ≥10 cells PASS, write `status: CALIBRATED` to `TRAILBLAZER-CALIBRATION.md` with timestamp + snapshot ID.
5. **Downstream gate activation**: `/rais-customer-voice-check` reads CALIBRATED state. UNCALIBRATED stamp removed from all skills.

**Operator-driven steps:**
- Run /jstack-eval (operator invokes; agent computes).
- Decide which cells (if any) to drop from v1 scope if iteration plateaus.
- Approve final calibration before tag.

Estimated time: 2-4 hours operator + 30-60 min CC per eval round.
