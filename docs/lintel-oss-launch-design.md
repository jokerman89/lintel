# Design: Lintel open-source launch — onboarding as a first-class system

Generated by /office-hours on 2026-06-08

## Problem statement

Lintel (v4.9) is built, CI-green, and dogfooded. The live question is no longer *build* — it is
*release*: how to take a company-neutral, pack-driven AI-CLI session harness open-source to a community.
The session reframed "is it ready / polished enough" into its true form: **the harness is ready; the
onboarding — which the chosen launch strategy bets everything on — is not.** Lintel's most fossilized
surface is `docs/getting-started.md`, which still opens *"Step-by-step for a new MS Sweden CAIP SE,"*
requires *"Microsoft SSO,"* and uses the dead repo slug. A 168-skill / 65-agent / pack-system harness is
not something a stranger adopts cold; the launch lives or dies on the first five minutes.

## What makes this cool (the value stack)

The operator named it cleanly, and it is genuinely strong:
1. **Way of working + built-in knowledge** — the 8-phase cycle, lessons/ADR memory, no re-explaining basics.
2. **Capability that boosts impact** — 168 skills + 65 agents + five engineering-domain modules.
3. **Shareable tools** — it's just skills + agents; teams share capability by sharing files.
4. **Safety at all levels** — compliance hooks, secret/customer-data blocks, pack-driven compliance mode.
5. **Identity per context** — packs/profiles: switch corp vs private per repo; voice, brand, persona, rules.

The novel architectural hook: **one source → eight CLI manifests.** Write skills/agents/hooks once, ship
to Claude Code / Codex / Cursor / Gemini / OpenCode / Copilot / Droid via thin per-CLI manifests.

## The user & the status quo

**First user (founder-for-own-pain — the strongest demand signal there is):** the operator built Lintel
because *their own* work sessions are unprotected while already using AI on internal company APIs and
subscriptions. The broader target: **IT-Pros at companies who need to add "straps" when using AI in the
CLI at work** — plus anyone who wants persona/identity and a versatile corp-and-private setup.

**Status quo:** AI is already used at work (internal APIs / paid subscriptions), but the *session* and
*what is done in it* are not protected — secrets, customer data, and ungoverned actions just happen. The
pain is real and self-experienced, but partly *latent* (it bites hardest on the first incident). The real
competitor is "we already use AI, unprotected, and hope."

## Strategic decisions (made this session)

- **Goal:** open-source / community release (not startup, not internal-only).
- **Wedge:** *whole harness + one killer onboarding* — do not ship a single-rope subset; bet that breadth
  becomes the wow if onboarding carries it. (The session flagged the "versatile for everyone" risk; the
  operator chose breadth-with-onboarding deliberately.)
- **Positioning:** **multi-CLI leads** the pitch as the differentiator — with the **honest capability tier
  table riding shotgun, up front, not buried.** Full on Claude Code / Codex / Cursor; supported on four
  more; **hooks are Claude-Code-only**. Stated up front this reads as confidence; discovered later it
  reads as bait-and-switch.
- **Launch approach:** **B — onboarding as a first-class system.**

## Premises (confirmed)

1. The harness itself (skills/agents/hooks/runtime) is GA-grade for Claude Code, CI-green, dogfooded. ✅
2. The launch is bet on onboarding carrying the breadth. ✅
3. Therefore "ready for users" = the onboarding exists and is great, *not* that the 168 skills are polished
   — and onboarding is currently the weakest, most-fossilized surface. ✅
4. Multi-CLI leads the pitch, with honest tiers stated up front (operator's refinement of premise 4). ✅

## Approaches considered

### Approach A — Clean the front door, ship in days · S/M · Low risk
The non-negotiable floor only: de-fossilize `getting-started.md`, a multi-CLI-leading README + honest tier
table, one tight quickstart, close the email/branding/`li-forge-stats` punch-list. Fastest respectable
launch; smallest diff. Con: 168 skills still reads as a wall — breadth listed, not felt.

### Approach B — Onboarding as a first-class system · L · Med risk · **CHOSEN**
Approach A's floor **plus** a `/li:welcome` guided-first-run skill that detects the CLI and runs a guided
first cycle, the showcase HTML as a landing page, and a ~90-second demo gif. A designed onboarding that
turns breadth into a gift and — because `/li:welcome` is CLI-detecting — makes multi-CLI the lead by
giving each CLI's user the right honest path. Con: most build effort; polishing the wrapper while the
single-pack reality and the 5 dropped customer agents wait.

### Approach C — Onboarding proves the thesis · M/L · Med risk
A's floor + a self-demonstrating onboarding ("run one real `/li:cycle`, watch discipline+safety happen")
+ a second public example pack to make multi-CLI/safety/packs tangible. Most differentiated for a
skeptical OSS audience; the second pack makes the moat concrete. Not chosen, but its **second-pack idea
is folded into Open Questions** because it is the cheapest way to make "switch profiles per repo" real.

## Recommended approach (CHOSEN): B — onboarding as a first-class system

The build, in dependency order. **This is design intent, not an implementation instruction — it is the
spec a future `/li:plan-eng-review` + build cycle executes.**

**Floor (must precede launch, table stakes):**
- Rewrite `docs/getting-started.md` from scratch, company-neutral, CLI-agnostic-first. Kill the "MS Sweden
  CAIP SE / Microsoft SSO / dead slug" content entirely.
- Close the identity punch-list from the State-of-the-Harness report: `@microsoft.com` → neutral email in
  `README.md`/`SECURITY.md` (and extend the `manifest-identity` tripwire to scan them so the guard stops
  giving false confidence); decide the manifest "MS-CAIP-SE" brand wording (neutral for an OSS spine);
  ship-or-de-claim `bin/li-forge-stats`.

**The first-class onboarding (the bet):**
- **`/li:welcome`** — a guided first-run skill. Detects the active CLI, prints the *honest* capability tier
  for that CLI, then walks the user through one real, tiny `/li:cycle` (or the closest thing the CLI
  supports) on a throwaory task so they *feel* the discipline + a hook firing, not read about it. It is
  itself a skill — dogfooding the "everything is a skill" thesis.
- **Per-CLI getting-started matrix** — one short page per CLI (install path + the honest tier + the one
  command that works), replacing the single fossilized doc. This is how "multi-CLI leads" stays truthful.
- **Showcase as landing page** — `bin/li-wiki-gen` already produces `docs/showcase/lintel-the-harness.html`
  with real counts; make it the public landing/marketing surface (and add a "state of the harness" view).
- **A ~90-second demo gif/asciinema** in the README hero — install → `/li:welcome` → a hook catching a
  secret → a clean `/li:cycle`. Showing, not listing.
- **README rewrite** — hero = multi-CLI differentiator + the honest tier table immediately below + the
  demo + a 3-line quickstart. The 168 skills become a "browse the catalog" link, never the front page.

## Open questions

1. **The 5 dropped customer agents** (`DemoNarratorJunior`, `ExecutiveBriefingDrafter`, `ProposalDrafter`,
   `RFPResponseDrafter`, `WorkshopFacilitator`) — silently dropped by the `customer/` gitignore shadow,
   now committable. Ship them (count → 70, regenerate) or keep local? Decide before the launch count is public.
2. **Single-pack reality** — only `_default` ships. The "switch profiles per repo, corp and private" pitch
   is a claim until a *second* real pack is public. Cheapest fix (Approach C's idea): ship one neutral
   example pack (e.g. a generic "startup" or "open-source-maintainer" pack) so `pack-switch` does something
   visible on day one. Strong candidate to fold into the launch even though B was chosen.
3. **Hooks Claude-Code-only** — the entire enforcement layer (the *safety* pillar) only fires on Claude
   Code. "Multi-CLI leads" + "safety is a pillar" are in tension on 7 of 8 CLIs. The `/li:welcome` tier
   message must say this plainly per-CLI.
4. **Brand/email values** — neutral maintainer email; whether "Lintel" stays the name; the MS-CAIP wording.

## Success criteria

- A stranger (not the operator) installs Lintel cold on their CLI and reaches a genuine "whoa" first-cycle
  moment in ≤5 minutes, with zero confusion attributable to a dead/MS-CAIP doc.
- The honest tier table is the *second thing* a visitor reads — zero "I came for Gemini support and hooks
  don't fire" bait-and-switch complaints.
- `/li:welcome` works on at least the three "full" CLIs and degrades honestly on the rest.
- The launch count (skills/agents/packs) is accurate and consistent everywhere (the v4.9 tripwires already
  guard this; extend to README/SECURITY).

work is *narrative + onboarding*, not pipeline. The one addition: a landing surface (the showcase HTML) and
the demo asset. CI/catalog regeneration is already wired.

## The Assignment

**Before you build any onboarding: sit behind exactly one real person — not you, not a teammate who already
knows Lintel — while they install it cold from the public repo on their own machine, and say nothing.**
Bite your tongue. Write down every single place they pause, squint, or ask "wait, what's a pack?" That
list *is* the `/li:welcome` script. You picked the strategy that bets the whole launch on onboarding; you
cannot design the killer onboarding from the inside, because you can no longer see the wall a stranger
hits. One cold install, watched in silence, is worth more than a week of polishing docs you wrote.

## Engineering-reviewed implementation plan: `/li:welcome`

`/plan-eng-review` on 2026-06-08. Scope: **`/li:welcome` as a thin orchestrator** (the floor and the
marketing assets are a separate PR / deferred — see NOT in scope). Six decisions, all to the
recommended option; no capability removed; reuse-first.

### Architecture decisions (confirmed)
- **A1 — tier single source.** Create `lib/cli-tiers.yaml` (per-CLI `tier` + capability flags:
  `hooks_supported`, `skills_native`, `subagents`). `/li:welcome` reads it; `bin/li-wiki-gen` *generates*
  the README capability table from it. Kills the prose-vs-reality drift class (same single-source pattern
  as the v4.9 `manifest-identity` fix). There is no machine-readable harness-tier today — `--cli-matrix`
  aggregates the finer *per-skill* `cli_support`, which cannot express "hooks only fire on Claude Code."
- **A2 — demo = `/li:cycle --dry-run`.** Reuse the existing dry-run (shows phases + would-fire hooks +
  token forecast, mutates nothing). A first-run welcome must not surprise-create job/plan/state artifacts.
- **A3 — hook demo degrades honestly, per CLI AND per hook-install-state.** Hooks ship inert/opt-in and
  fire only on Claude Code, so the headline "watch a hook fire" is the least-available thing at first run.
  Three branches: Claude-Code + hooks-installed → real fire; Claude-Code + no-hooks → *print* the install
  snippet (Q1) then fire; other CLIs → narrate "this is what fires on Claude Code, the only CLI with the
  enforcement layer." This ties the demo to the A1 tier message.
- **A4 — discovery via README quickstart + install/`li-scaffold` completion output** pointing to
  `/li:welcome`. No auto-launch / SessionStart surfacing (deferred).
- **Q1 — print-the-snippet, no auto-mutation.** `/li:welcome` prints the `ln -s` + `settings.json` hook
  entry for the user to run; it does NOT auto-edit `~/.claude/settings.json` on first run (auto-mode
  boundary on settings; avoids clashing with their existing hooks).
- **Test design — testable shell lib.** Extract `cli_tier_field <cli> <field>` into `lib/cli-tiers.sh`,
  sourced by BOTH `/li:welcome` and `li-wiki-gen` (one parser, not two), with a unit test. The riskiest
  logic (the tier lookup) becomes testable + single-source.

### What already exists (reuse — do not rebuild)
- `/li:cli-fingerprint` — CLI detection (env-var → process → tool-probe → config). **Delegate.**
- `/li:cycle --dry-run` — the guided demo. **Reuse.**
- `bin/li-doctor` — installed-CLI + per-CLI install-state detection (for the hook-install-state branch).
- `bin/li-wiki-gen` — extend to generate the README tier table from `cli-tiers.yaml`.
- `scaffolding/01-foundation/TEMPLATE-skill.md` — the new-skill scaffold.
- `tests/shape/manifest-identity.sh` + `handoff-cap-wired.sh` — the patterns the new sync/wiring tests copy.

### NOT in scope (deferred, with rationale)
- **The floor** (rewrite `getting-started.md`; `@microsoft.com`→neutral email in README/SECURITY + extend
  the `manifest-identity` tripwire to scan them; manifest "MS-CAIP-SE" brand wording; ship-or-de-claim
  `li-forge-stats`) — separate mechanical identity-hygiene PR; it is the *launch blocker*, but it is not
  engineering and shouldn't gate this skill's review.
- **Marketing assets** (demo gif, showcase-as-landing, per-CLI getting-started matrix) — deferred.
- **The 5 dropped customer agents** + **a second example pack** — open product decisions from the design
  doc above, not part of `/li:welcome`.
- **`bin/li-hook-install` helper** (Q1 alt) and **a first-run SessionStart surfacing hook** (A4 alt) —
  fine later features; not first-run, not now.

### Failure modes
| Codepath | Realistic failure | Test? | Handled? | Visible? |
|---|---|---|---|---|
| `cli-fingerprint` returns unknown CLI | welcome has no tier to show | `tests/unit/cli-tiers.sh` (unknown→safe default) | fall to generic "unrecognized CLI, manual path" | loud, honest |
| `cli-tiers.yaml` missing/malformed | `cli_tier_field` returns garbage/crashes | unit test | safe default = `degraded` | loud |
| README tier table drifts from `cli-tiers.yaml` | the one skill about honesty lies | `tests/shape/cli-tiers-sync.sh` (CI) | regenerate via wiki-gen | caught in CI |
| `/li:cycle --dry-run` unavailable on a non-full CLI | demo can't run | (A3 narrate branch) | narrate instead of invoke | honest |

No silent-failure critical gaps: every failure path either has a test, a safe default, or an honest
narration — by design (the skill's whole job is honesty).
