## Leaf evidence

### T1: Consequence decision

`assess_depth` implements the six axes and values from the spec exactly.

**Context validation**

- The context's keys must be exactly `schema_version`, `facts`, `evidence` and `asserted_by`.
- `schema_version` must be the integer 1. The boolean `True` is refused.
- Every known fact needs a nonblank evidence reference.
- Evidence entries are refused for undeclared facts.
- `asserted_by` needs a nonblank `actor` and `reference`.
- Boolean axes accept only real `True`/`False` or `"unknown"`. They refuse `1`, `0` and `"true"`. Other axes refuse booleans and integers.

**Depth floors**

- Deep is the minimum for any of: `deployment=production`, `exposure=untrusted`, `impact=sensitive` or `impact=irreversible`, `security_boundary=true`, `blast_radius=shared`.
- Lean requires all of: every fact known, `deployment` local or internal, `exposure` isolated or trusted, `impact=reversible`, no behavior change, no security-boundary change, and `blast_radius=contained`.
- Other known cases get standard.
- Unknown or absent facts get at least standard, with `status: needs-context`.
- No context at all gets standard with `needs-context`.

**Requests and tags**

- An explicit lower depth raises `DepthRefused`. A higher depth is allowed and recorded as a reason.
- `deep-review` is added when the selected depth is deep.
- `production` is added when `deployment=production`.
- `security-critical` is added for untrusted exposure, sensitive or irreversible impact, or a changed security boundary.
- `risk-unknown` is added whenever any fact is unknown, at every depth.

**Result**

- Every result sets `release_clearance: false`.
- Every result carries `authority`, with model selection, MARS consent and execution authorization all false.
- `recommended_independence` is `independent` for lean and standard, and `independent-staged` for deep.
- The result has no line-count score and makes no model call, network request or permission claim.

### T3: Optional pattern consumer

`prepare_pattern_review` loads the provider lazily, and only from the trusted sibling file `lib/patterns.py`:

- It uses `importlib.util.spec_from_file_location` under the private module name `_lintel_review_context_patterns_provider`. It never uses `sys.path` or an ambient `patterns` module.
- On Python below 3.10 it returns `provider_python_unsupported`. The provider's contract requires 3.10+; the core module is 3.9-compatible.
- A missing or linked file returns `provider_missing`.
- A load exception returns `provider_load_failed`, and the module is removed from `sys.modules`.
- Missing API names return `provider_incompatible`.
- Each of these returns `status: unavailable` before any user input file is read.

When the provider is available, the adapter uses only the provider's own functions:

1. Input reading: `Reader.read(kind="input")` with `LIMITS.input_bytes` (`catalog_bytes` for the lock), then `parse_json`, mirroring `li-pattern`.
2. Parsing: `parse_roots`, `parse_context` and `parse_attestations`.
3. Verification: `verify_lock`.
4. Projection: `project_package`, called only when verification returns `ok`. The task map is read only after verification succeeds.
5. Coverage: `review_coverage`, called only when coverage evidence is supplied.

Provider statuses and diagnostics pass through, as does `PatternError.status`. After verification succeeds, the top-level
`diagnostics` always contains the verification diagnostics (including warnings such as `pinned_deprecated`), then the
projection's, then the coverage report's. Only exact duplicate dicts are dropped, because `review_coverage` re-reports its
own verification diagnostics. The following are returned as provider-validated data copied verbatim, only after
verification succeeds:

- the projection, including every clause, its level/state, settings and original task IDs;
- the coverage report;
- the lock's `exceptions`;
- the lock's `asset_pins`, as `asset_refs` metadata.

The adapter does not:

- reinterpret mandatory, default or waived clauses;
- truncate anything;
- rewrite locks, fall back, re-resolve, parse pack YAML or infer an empty catalog;
- read assets or fetch from the network.

The top-level `release_clearance` is always false, and a `limits` text marks the output as supplemental ADR-0028 context. The only test seams are the private in-process `_provider_double` and `_provider_path`. There is no CLI or environment override.

### T4: Pattern boundary tests

These tests are labeled as using a **PROVIDER DOUBLE** or synthetic provider files. They are not live acceptance evidence. They cover:

- An absent provider is `unavailable` (not `empty`) even when every input file is deleted, which proves no input read happens first.
- An ambient `patterns` in `sys.path` or `sys.modules` is ignored.
- The Python-version gate.
- Broken and partial provider files.
- The loaded module comes from the trusted file under the private name, not from an ambient decoy.
- The real sibling is checked in its observed state, with no skip. If it is absent, the result must be `provider_missing`/`unavailable`. If it is present, it must load as the trusted file with every required API name (or report `provider_python_unsupported` below 3.10). The real verify/project/review join remains coordinator T11.
- A failed verification (`conflict`, `unavailable`, `needs-context`) causes no projection or coverage call, no task-map read and zero asset reads, and leaves exceptions and assets null.
- A verified projection of 300 mandatory clauses of about 3 KB each is returned verbatim and untruncated, with settings, tasks, exceptions and asset metadata preserved, and verify is called before project.
- Coverage `ok` and `review-unmet` propagate, with attestations passed to both verify and coverage.
- Verification warnings reach the top-level diagnostics exactly once, with and without coverage, in the order verify, projection, coverage.
- A provider `PatternError` keeps its status, and verify is not called.
- Blank or non-string package values and missing inputs are refused, and the inputs are keyword-only.
