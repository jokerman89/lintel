## Findings

### P05-S01 - P1: malformed later direct decisions silently retain older clearance

**Locations:** `bin\li-review-evidence.py:68-71`;
`lib\review_contract.py:549-556`. **Confidence:** 10/10.
**Requirements:** A03.1/A03.3/A03.4, ADR-0028, RU-01.

`audit_records` accepts direct JSON objects without validating their discriminator
or versioned shape. `select_latest` then skips a record whose `skill` is missing,
null or empty before evaluating its scope or validity. Append such a later v1
`fail` decision with the identical work map, package and full context after a valid
PASS: the real shell reader and real SHIP command both return **exit 0, `ok: true`**,
using the older decision and its older corroboration.

All three variants were independently reproduced. The ordinary writer rejects
these malformed inputs; the defect is the reader/shared selector accepting and
discarding malformed direct records already in its supported log representation.
This is a fail-closed/parser requirement, not a claim that the log authenticates
its authors or resists an actor allowed to rewrite it.

**Required correction:** validate direct decision discriminators/shape before
scope filtering, and treat ambiguous malformed decisions as unresolved rather
than unrelated. Preserve legitimate other-skill/package records and explicitly
imported historical records. Add the three cases through the actual reader and
SHIP, not just the pure validator.

Executable replay from this candidate's repository root, in PowerShell:

```powershell

@'

from pathlib import Path

        read = f.read(ok=None)

        print(variant, "read", read.returncode, json.loads(read.stdout)["ok"],
              "ship", ship.returncode, json.loads(ship.stdout)["ok"])
finally:
    f.doCleanups()
'@ | python -
```

Observed for each variant: `read 0 True ship 0 True`. Correct behavior is blocked,
without reviving the older PASS. All repositories, actor receipts and observations
in this replay are synthetic test fixtures.

### P05-S02 - P2: selected-package completion bookkeeping invalidates unchanged acceptance

**Locations:** `lib\review_contract.py:464-471,582-590`.
**Confidence:** 10/10.
**Requirement:** A03.5 and the explicit completion-bookkeeping preservation check.

The supported acceptance excerpt still hashes raw task-status bytes. In a fixture
with `acceptance_paths` selecting `{"path":"plan.md","start":"# P1","end":"# P2"}`,
alongside unchanged `spec.md`, the exact `plan.md` fixture was:

```markdown
# P1
- [ ] A1 Fix fixture
- [ ] A2 Preserve config
Acceptance: verify selected fixture and preserve config.
# P2
- [ ] unrelated
```

After a passing writer/reader/QA/SHIP round trip, changing only
`- [ ] A1 Fix fixture` to `- [x] A1 Fix fixture` made reader and SHIP both exit 3
with `Selected work/acceptance sources changed`. Product inputs, IDs, task wording
and acceptance criteria were unchanged; the plan was not a selected product file.

The existing test proves reuse for bookkeeping in an *unselected* P2 section,
not ordinary completion of the reviewed P1 leaves. Thus completing the selected
work invalidates its evidence and can force another review/context cycle merely
to acknowledge completion.

**Required correction:** provide an explicit acceptance identity that separates
authorized completion/status metadata from the original leaf requirements, while
retaining the authoritative task source/history. Do not blanket-exclude plans,
configuration or `.claude`. Test selected-leaf checkbox/status-only reuse alongside
a changed selected criterion that must still block. The latter negative also
returned exit 3 in this review's probe.

### P05-S03 - P2: QA invents a mandatory executable-test gate for documentation-only work

**Location:** `lib\review_contract.py:667-676`. **Confidence:** 10/10.
**Requirements:** A03.3 and genuine not-applicable/doc-only preservation.

`verify_qa` always requires an applicable mandatory `tests` control, independently
of the approved acceptance. A mapped documentation-only fixture declared D1
proofreading, explicitly no executable test gate, a passing mandatory documentation
control, and a source/version/reason/evidence-grounded tests N/A. Shared control
evaluation returned `blocked: false`; the review reader cleared the exact context.
Nevertheless `qa` exited 1 and SHIP exited 3 with
`QA has no required executed test scope`.

The prepared context's `required_controls` was exactly `["documentation"]`.
The QA input reused these two actual fixture controls:

| ID | Kind | Requirement | Applicability | Status |
|---|---|---|---|---|
| documentation | check | mandatory | applicable | pass |
| tests | tests | mandatory | not_applicable | unverified |

Both referenced the existing `checks.txt` fixture evidence and `spec.md` policy
version `fixture-1`. The tests reason was `Approved documentation-only acceptance
explicitly requires no executable test gate.` Its policy applicability pointed to
the non-executable documentation acceptance in `spec.md` and `plan.md`.
QA emitted no record on stdout; stderr was:

```text
li-review-evidence: QA has no required executed test scope
```

To exercise the SHIP consumer separately, the fixture supplied a schema-conformant
QA envelope with the same `context_digest`, these controls and their actual hashed
evidence manifest. It was synthetic fixture input, not a falsely claimed successful
QA emission. Actual SHIP output, exit 3:

```json
{"ok":false,"problems":["li-review-evidence: QA has no required executed test scope"],"status":"error"}
```

This is not a missing-test success request: no executable test is an actual
requirement in that fixture. The useful unmapped `snapshot`/`inspect` path already
works and is not implicated.

**Required correction:** derive QA obligations from the approved, bound acceptance
and actual applicability. Permit verified non-test/documentation checks when tests
are genuinely N/A, without demanding fabricated counts or a redundant plan.
An actual applicable mandatory test gate with zero runs, skips, errors or missing
evidence must remain blocked.

### P05-S04 - P2: SHIP still upgrades configured advisory gates to hard requirements

**Locations:** `skills\ship\SKILL.md:94-98,108-120,273-282`.
**Confidence:** 9/10. **Requirement:** A02.2 and WF-01.

The new rule at lines 79-83 correctly separates mandatory and advisory controls,
but the executable workflow instructions still say `If ANY gate violation: HARD
STOP`, require `All configured gates must PASS for customer-shippable`, and repeat
the all-gates/ANY-violation rule in completion/pause criteria. A configured advisory
voice or brand finding therefore encounters a contradictory mandatory-pass rule.

The helper's advisory-failure round trip passes, as it should. This finding is the
remaining instruction-contract conflict, not a claim that a live model was
observed following the wrong branch.

**Required correction:** qualify these later branches with applicability and the
actual mandatory requirement, consistently retaining advisory results as advice.
Align workflow examples/status conditions with the shared evaluator; do not remove
the customer-share checks or weaken a genuinely mandatory policy.
