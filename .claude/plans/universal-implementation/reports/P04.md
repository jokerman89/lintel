### Link preservation and platform semantics

The pre-repair `swarm_snapshot.py` explicitly rejected Git `120000` and `160000` modes; its
file-only path could follow internal file links. F04 does **not** remove the useful link case.
It preserves file-only links and adds data-only Git symlink support: a newly reviewed `120000`
entry binds its exact target text/bytes and type, not the bytes of the file it points at.
Directory links remain single data entries; target contents are not added to the snapshot.
Containment resolution is only an escape check, not permission to follow/read/execute a target.
Outside-root targets, traversing linked parent directories, unsupported reparse forms and
submodules remain refused.

Positive tests cover unchanged native Git symlinks, a faithful target-file checkout under
`core.symlinks=false`, file-only links, and an internal directory target with no target-content
capture. Changing only the exact target string invalidates the previous binding. A same-content
regular-to-link change still invalidates the old regular-file result; preserving links never
preserves stale type evidence.

Windows `core.filemode=false` uses the Git index mode rather than unreliable filesystem execute
bits; both staged and committed index-only mode changes are tested. The POSIX filesystem-chmod
branch is retained in the test for platforms that support it but was not executed on Windows.
Regular UTF-8 content retains CRLF normalization; binary content and link-target bytes are exact.
No permissions are granted by equal metadata. Git submodules (`160000`) were already unsupported
in `dca635d` (`swarm_snapshot.py:100-101`); no supported submodule workflow was removed.

Existing content-only snapshot records cannot supply missing type/mode evidence and must be
recaptured and reviewed for a new attempt; no original report is silently rewritten or upgraded.
This is still the local P04 integration seam, not a permanent competing P05 snapshot definition.
A22.7 must consume the finalized shared contract.
